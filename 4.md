STAGE 4 — CLOUDFLARE WORKERS / OPENNEXT PREPARATION & DEPLOYMENT HARDENING

This stage is ONLY about making the existing Reachzy Next.js application deterministically ready for Cloudflare Workers.

DO NOT deploy to production yet.

DO NOT make visual/content changes.

DO NOT redesign anything.

DO NOT migrate the application to another framework.

==================================================

The target architecture for THIS stage is:

==================================================
4. CLOUDFLARE CONFIGURATION MUST HAVE ONE SOURCE OF TRUTH
==================================================

The repository must contain an explicit Wrangler configuration.

Do NOT depend on Cloudflare/Wrangler automatic project detection during deployment.

Do NOT intentionally remove the Wrangler configuration and rely on:

`npx wrangler deploy`

to generate one.

Do NOT allow deployment to silently rewrite the project's architecture.

The final repository configuration must explicitly describe the Worker.

Use JSONC unless the existing project has a compelling documented reason to use another supported format.

The configuration must be internally consistent.

==================================================
5. WORKER IDENTITY
==================================================

The intended Worker identity is:

`reachzy-website`

Treat this name as intentional and important.

Search the ENTIRE repository and deployment configuration for:

- `reachzy`
- `reachzy-website`
- `WORKER_SELF_REFERENCE`
- service bindings
- Worker references
- generated names
- deployment names

There must not be an accidental mismatch where one configuration references:

`reachzy`

while the actual Worker is:

`reachzy-website`

Do not rename the intended Worker merely to make an error disappear.

Resolve the underlying mismatch.

==================================================
6. OPENNEXT OUTPUT
==================================================

The deployment pipeline must deterministically create:

`.open-next/worker.js`

and the corresponding:

`.open-next/assets`

before Cloudflare deployment is attempted.

This is a critical gate.

After configuring OpenNext:

1. remove/clear stale generated output if appropriate
2. run the correct OpenNext production build
3. verify `.open-next/worker.js` physically exists
4. verify `.open-next/assets` exists
5. inspect the generated output enough to confirm it is a real production build
6. only then consider the project deployment-ready

A successful `next build` by itself is NOT sufficient.

The previous failure where `next build` succeeded but Wrangler later reported:

`.open-next/worker.js not found`

must not be reproducible.

==================================================
7. OPENNEXT CONFIGURATION
==================================================

Use the current officially supported OpenNext Cloudflare adapter for the existing application.

Inspect the installed version before deciding configuration details.

If `@opennextjs/cloudflare` is missing, install it deliberately and record the exact version.

If Wrangler is missing or unsuitable, install/pin an appropriate version deliberately.

Do not blindly use unpinned `@latest` installs if doing so would make the build non-reproducible.

Preserve the existing package manager and lockfile.

Do not introduce unnecessary dependencies.

The OpenNext configuration must be explicit and repository-controlled.

==================================================
8. WRANGLER CONFIGURATION
==================================================

The Wrangler configuration must explicitly define the Worker and OpenNext output.

Verify the configuration includes the equivalent of:

- Worker name: `reachzy-website`
- main entry: `.open-next/worker.js`
- compatibility flags appropriate for OpenNext/Next.js
- assets directory: `.open-next/assets`
- assets binding appropriate for the adapter

Use the current official Cloudflare/OpenNext requirements rather than copying an obsolete configuration from an old log.

Do not blindly copy historical configuration.

Historical logs are evidence of what happened, not automatically evidence of what SHOULD be used now.

==================================================
9. COMPATIBILITY DATE
==================================================

Use an explicit compatibility date appropriate for the current Cloudflare/OpenNext setup.

Do not leave the project dependent on an accidental/default date.

Use the current official documentation and the installed adapter requirements when selecting it.

==================================================
10. PACKAGE SCRIPTS
==================================================

Create deterministic scripts for the Cloudflare workflow.

The repository should have an obvious separation between:

normal Next.js development/build

and

Cloudflare/OpenNext preview/deployment.

The intended workflow should be understandable from `package.json`, for example:

development
→ normal Next.js development

Cloudflare preview
→ OpenNext build
→ Workers-runtime preview

Cloudflare deployment
→ OpenNext build
→ verify generated Worker output
→ deploy

Do not create scripts that hide failures.

A deployment script must fail when the OpenNext worker output was not generated.

==================================================
11. NO RAW DEPLOYMENT BEFORE OPENNEXT BUILD
==================================================

Do not create a workflow where:

`wrangler deploy`

is executed against the project expecting Wrangler to figure out the Next.js/OpenNext architecture.

The deployment flow must explicitly produce the OpenNext Worker output first.

The deployment command must use the repository's intended OpenNext deployment path.

Do not rely on automatic framework detection.

==================================================
12. SELF-REFERENCE / SERVICE BINDING AUDIT
==================================================

Because historical deployment attempts produced a:

`WORKER_SELF_REFERENCE`

failure, investigate this explicitly.

Search configuration and generated files for:

- self-reference configuration
- service bindings
- Worker service names
- `reachzy`
- `reachzy-website`

Determine whether the current application actually requires a Worker self-reference.

If it does NOT require one:

remove unnecessary self-reference configuration safely.

If the OpenNext adapter requires a specific self-reference mechanism:

configure it explicitly and make sure the referenced Worker name exactly matches:

`reachzy-website`

Do not add service bindings merely because they appeared in an old configuration.

Do not invent architecture solely to silence an old error.

Document the final decision and why.

==================================================
13. AUTOMATIC CLOUDFLARE CONFIGURATION
==================================================

The previous deployment history shows that automatic configuration created or changed files and contributed to configuration drift.

Therefore:

Do not run a command solely to "see what Cloudflare automatically generates."

Do not allow an automatic migration to replace the repository's explicit configuration.

If a tool proposes to modify configuration automatically:

STOP and inspect exactly what it wants to change.

Accept changes only when they are intentionally equivalent to the documented architecture.

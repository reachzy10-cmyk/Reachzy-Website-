STAGE 3 — FULL WEBSITE STABILIZATION, INTEGRATION & QA

The `/for-creators` implementation has now been handled separately.

This stage is about making the ENTIRE Reachzy website stable and production-ready BEFORE touching Cloudflare deployment configuration.

Do not deploy anything in this stage.

==================================================
1. READ PROJECT CONTEXT AGAIN
==================================================

Before editing, re-read:

- `/archive/REACHZY_DEV_CONTEXT.md`
- relevant `/reference` files
- especially the historical deployment logs
- current git status
- current source tree

Do not assume your previous context is sufficient.

Use the reconstructed context and historical records as the basis for decisions.

==================================================
2. AUDIT EVERY ROUTE
==================================================

Inspect and test:

- `/`
- `/for-creators`
- `/for-brands`
- `/creators/ai-learners-india`
- `/_not-found`
- `/sitemap.xml`

For every route, check:

- compilation
- rendering
- runtime behaviour
- console errors
- hydration errors
- broken imports
- missing assets
- invalid component usage
- broken links
- responsive behaviour
- shared navigation
- footer
- typography
- spacing
- buttons
- animations
- images
- metadata where applicable

Do not only inspect source code.

Actually render/test the pages wherever browser/dev-server tooling is available.

==================================================
3. FIX EXISTING TECHNICAL PROBLEMS
==================================================

Resolve any remaining problems caused by the previous development history, including problems such as:

- invalid Lucide imports
- incorrect component/data contracts
- malformed JSX
- broken dynamic components
- bad props
- missing exports
- incorrect asset paths
- hydration mismatches
- TypeScript errors
- runtime rendering errors
- broken mobile layouts

Use the smallest safe fix.

Do NOT perform unnecessary refactors.

Do NOT replace the architecture.

==================================================
4. TYPESCRIPT / BUILD INTEGRITY
==================================================

Determine whether the project is still using temporary TypeScript workarounds such as:

`ignoreBuildErrors`

If real TypeScript problems still exist, fix them properly.

Do not hide errors merely to make the build pass.

The final project should pass its normal type/build validation without relying on a workaround unless the existing project context explicitly documents a justified exception.

Do not silently change compiler settings just to suppress errors.

==================================================
5. DESIGN CONSISTENCY
==================================================

Compare all pages against the established Reachzy visual language.

Pay particular attention to:

- dark background treatment
- typography
- spacing rhythm
- borders
- cards
- buttons
- section transitions
- navigation
- footer
- imagery
- motion

The website should feel like ONE product/site.

Do not redesign pages merely because you personally prefer another style.

Use `/reference` when determining previous styling decisions.

The goal is consistency, not novelty.

==================================================
6. /FOR-CREATORS FINAL CHECK
==================================================

Re-check `/for-creators` specifically.

Verify:

- approved copy remains intact
- no unsupported claims
- no fake creator/client relationship
- exact 15–20% figure is NOT displayed
- exactly one primary "Talk to Reachzy" CTA exists
- CTA is at the end
- fallback email is visible
- opportunity briefing is illustrative only
- AI Learners India information is presented according to the approved source
- mobile layout works
- desktop layout works
- no accidental redesign occurred

==================================================
7. LINKS AND ASSETS
==================================================

Perform a systematic check of every internal link and major asset.

Look for:

- 404 links
- incorrect routes
- missing images
- missing icons
- broken external links
- incorrect `href`
- incorrect `src`
- duplicate or obsolete assets

Do not remove assets merely because they appear unused without checking whether they are referenced dynamically.

==================================================
8. ACCESSIBILITY / BASIC UX
==================================================

Check obvious production issues:

- buttons are actually clickable
- links are distinguishable
- images have appropriate alt text
- keyboard navigation is not obviously broken
- focus states exist where appropriate
- text remains readable
- interactive elements are not too small on mobile
- animations do not block interaction

Do not turn this into a large accessibility rewrite.

Fix clear issues only.

==================================================
9. PERFORMANCE / DEPENDENCY DISCIPLINE
==================================================

Inspect package.json and the lockfile.

Do not install packages unless genuinely required.

Identify unnecessary newly introduced dependencies.

Do not replace working libraries.

Keep the project lightweight.

==================================================
10. BUILD + RUNTIME VALIDATION
==================================================

Run the project's normal validation commands.

At minimum determine the correct commands for:

- lint
- type checking
- production build

Then run them.

Also start the production/dev server as appropriate and actually inspect the important routes.

A successful build alone is NOT sufficient.

==================================================
11. GIT DIFF AUDIT
==================================================

Before completing the stage:

- inspect `git diff`
- inspect `git status`
- confirm no accidental files were changed
- confirm `/reference` was not modified
- confirm archive/historical evidence was not modified
- confirm no secrets were introduced
- confirm no `.env` contents were committed
- confirm no generated deployment artifacts were accidentally committed

==================================================
12. DO NOT TOUCH DEPLOYMENT YET
==================================================

DO NOT:

- deploy
- change Cloudflare Worker configuration
- switch hosting platforms
- switch Next.js architecture
- introduce a new deployment framework
- run random Wrangler/OpenNext migrations
- allow Cloudflare auto-configuration to rewrite the project
- modify deployment files just because they exist

Cloudflare preparation is the NEXT stage.

==================================================
13. FAILURE RULE
==================================================

If ANY important validation fails:

STOP.

Fix the problem.

Re-run the affected validation.

Do not continue while a known critical runtime/build problem remains.

==================================================
14. COMPLETION REPORT
==================================================

Report:

- routes inspected
- issues found
- issues fixed
- files changed
- dependencies changed, if any
- build/type/lint results
- browser/runtime results
- responsive results
- remaining known issues
- exact git status

Then STOP.

Do not begin Cloudflare preparation.

Do not deploy.

Wait for the next stage.
